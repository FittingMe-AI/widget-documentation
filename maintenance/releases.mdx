Your installation depends on the loader, widget, and API working together. Record the storefront release and configuration used for your acceptance test, and review integration notices from FittingMe before rolling out related changes.

## Current published compatibility baseline

| Surface | Current contract covered by this guide |
| --- | --- |
| Loader asset | `https://widget.fittingme.ai/v4/fittingme-loader.js` |
| Try-on widget | `https://widget.fittingme.ai/tryon/` |
| Public API base | `https://api.fittingme.ai` |
| Supplied-image messages | `fittingme/4`, with `loader_major=3` |
| Catalogue-only messages | `fittingme/4`, selected by the loader when no image is supplied |

The canonical `/v4/` asset selects `fittingme/4` for both image and catalogue embeds. Upgrade all page tags and consumer callbacks together; an asset path and a wire major remain separate contracts. Deploy and verify the dual-dialect widget and both loader paths before releasing migrated consumers or publishing these examples.

The hosted loader URL is stable and does not contain a content hash. It is not a pin to an immutable release. Avoid an additional permanent cache or vendored copy that can outlive compatible widget/API changes.

## Photo Refusal — dev rollout, 9 October 2026

The reader, refusal/advice screens, phone handoff recovery, provider refusal handling, catalogue exclusions and refusal fact are deployed to dev. Dev is in `project`: shoppers see guidance, while server launch and saved-collection enforcement remain disabled after two latency-gate failures.

This campaign did not promote product services to staging or production. Confirm availability for your storefront before rollout. No new loader attribute or browser event is required. Data consumers should allow the announced `tryon_photo_refused` addition in [Delivered Events](/reference/events#delivered-events-and-photo-refusals), with the existing eight columns and no reason or origin.

Read [photo recovery](/troubleshooting/symptoms#a-photo-is-refused-or-receives-advice), [product exclusions](/integration/products#when-try-on-is-unavailable) and [acceptance checks](/testing/journey#verify-photo-guidance-in-an-enabled-environment).

## Draft v5 multiple-view compatibility

The unpublished v5 integration uses `/v5/fittingme-loader.js`, `fittingme/5` English messages and `data-garment-image-urls` for one URL or several ordered views of the same product and colour. The loader requires explicit capability acknowledgement from the widget and API. Confirm that all three are available in your assigned environment before using the new attribute. Usable catalogue imagery takes priority over supplied views; invalid supplied configuration may still use eligible catalogue imagery.

`data-garment-image-url` remains a deprecated one-photo alias. **1 December 2026 is a migration target, not a cutoff.** Support continues until removal is separately announced. See [loader configuration](/reference/configuration) for parsing and precedence.

## Existing v4 supplied-image compatibility

The existing v4 supplied-image integration adds `data-garment-image-url`. It requires major-4 messaging in both directions. An older loader can reject the attribute, and an incompatible widget can refuse the protocol. Its existing image-bearing behavior does not silently downgrade to catalogue lookup.

When enabling this input on an existing installation, verify the assigned environment supports it and rerun the [complete journey checks](/testing/journey).

## Release-note information to act on

For an announced change, identify the affected configuration, methods, event fields, browser behaviour, and required migration steps. Distinguish a documentation clarification from a behaviour change. Confirm when a change is available in your storefront's environment.

For the rollout date of a specific fix or a retailer-specific migration, obtain confirmation from FittingMe for the environment your storefront uses.

Use [update, disable, or remove FittingMe](/maintenance/updates) for the operational steps.
