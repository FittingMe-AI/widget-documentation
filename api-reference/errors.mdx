Every backend response with an HTTP error status uses an RFC 9457 Problem Document and the `application/problem+json` media type. Members are placed at the document root; there is no enclosing `error` object.

## Response shape

```json
{
  "type": "https://fittingme.ai/problems/validation_error",
  "title": "Validation failed",
  "status": 400,
  "detail": "The photo field is required",
  "instance": "/v1/widget/handoff",
  "code": "validation_error",
  "field": "photo"
}
```

| Member | Type | Meaning |
| --- | --- | --- |
| `type` | string | Stable URI identifier for the problem class. |
| `title` | string | Stable summary associated with `type`. |
| `status` | integer | HTTP status repeated in the response body. |
| `detail` | string | Human-readable detail for this occurrence. Do not branch on it. |
| `instance` | string | Request path for this occurrence, without the query string. |
| `code` | string | Final path segment of `type`, derived structurally rather than mapped separately. |
| `field` | string | Optional extension present only for field-specific `validation_error` responses. |
| `capability` | string | Optional extension present only for `capability_not_entitled` responses. |

The query string is deliberately excluded from `instance`, so a credential such as a relay token cannot be reflected into an error body.

## Type URIs are identifiers, not links

Values below the `https://fittingme.ai/problems/` base are stable identifiers. They are not dereferenceable documentation links, and no FittingMe environment serves pages at those paths. Do not open or fetch a `type` URI. Use this page as the human-readable reference for every identifier.

`code` always matches the final segment of `type`. The shared Problem Document constructor derives both values from one input, so callers cannot construct them independently.

<Note>
  Business validation uses `validation_error` with status `400`. Status `422` is reserved here for `invalid_body_field`, an extractor rejection; it is not an alternate status for business validation.
</Note>

## Handle errors by stable identifier

Branch on `code` or `type`, not on `title` or `detail`.

<Accordion title="JavaScript handling example">

```javascript
async function readJson(response) {
  if (response.ok) return response.json();

  const problem = await response.json();

  if (problem.code === 'validation_error' && problem.field) {
    console.error(`Invalid field: ${problem.field}`);
  }

  throw Object.assign(new Error(problem.detail), problem);
}
```

</Accordion>
